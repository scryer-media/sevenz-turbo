# Benchmarking

The reason this fork exists is decode throughput, so the swap is only done when
it is measured. This page records how to measure it and what the numbers were
when the codec swap landed.

For current numbers on any host, use
[`bench/sevenz-turbo-bench`](../bench/sevenz-turbo-bench/README.md): one Go
binary that generates the corpus with the host's `7zz`, runs the whole matrix
(container parse, LZMA/LZMA2 decode across a thread sweep, the memory budget,
solid and non-solid archives, AES-256 in both cryptography builds, the
filters, and LZMA2 encode across levels with the size ratio) against `7zz` as
separate measured processes with peak RSS on every row, and merges several
hosts' reports into one. It drives `decode-bench op ...` (below). Every result
under [Results](#results) predates it.

## The harness

`tools/decode-bench` is a workspace member (not an example) because it depends
on upstream `sevenz-rust2` in order to time the fork against it, and that
dependency must not appear in this crate's own graph.

```console
$ cargo build --locked --release -p decode-bench
$ ./target/release/decode-bench --runs 3 path/to/st.7z path/to/mt.7z
```

For each archive it runs, in one session on one machine:

| Decoder | What it runs |
| --- | --- |
| `7zz t (all)` | the C reference with every thread it wants, full decode plus CRC check |
| `7zz t -mmt=1` | the same, single-threaded |
| `sevenz-rust2 0.22.2` | the upstream release the fork was taken from, every entry to a sink |
| `sevenz-turbo @N` | this fork at N threads, same code path |
| `sevenz-turbo @N no crc` | the same with `set_verify_checksums(false)`, to price verification |

`--threads 1,2,8,all` chooses the thread counts; `--only fork` and
`--no-oracle` cut the run down to this crate while bisecting something.

`decode-bench op version|list|decode|encode` is the machine-facing mode
`bench/sevenz-turbo-bench` drives: exactly one operation per process (a header
parse, a full decode on the convenience or the single-parse streaming path,
optionally under `--memory-limit` or with the upstream engine, or an encode
at a level and thread count), printing one JSON line, so the caller can take
the operation's peak RSS from the exited process. `op version` reports the
crypto backend, which LZMA encoder is linked (`lzma_encoder`), the Cargo build
profile, the commit and whether the tree was dirty, the lock file's SHA-256,
the locked `lzma-turbo`, `sevenz-rust2`, `aws-lc-rs` and `crc-fast` versions,
and every `ppmd-*` crate the lock carries with its version (`ppmd_crates`, and
`ppmd_turbo` on its own); the harness refuses a candidate that was not built
with the `release` profile.

It reports the median wall time of `--runs` repetitions, the MiB/s of
*uncompressed* output, and a 64-bit digest of the extracted bytes, so "the two
libraries agree" is shown rather than assumed. A byte-at-a-time CRC-32 in the
sink was the harness's first version and cost a quarter of the measured time —
if you change the digest, check with `sample(1)` that it has not become the
thing you are measuring.

The fixtures of the results below are the ones `lzma-turbo` uses
(`bench/fixtures/st.7z`, `mt.7z`: 1 GiB of synthetic payload at `-mx5`,
written `-mmt=1` and `-mmt=on` respectively). They are ~900 MiB each, were
generated by `cargo xtask fixtures` in `lzma-turbo`, and are deliberately not
in this repository. `sevenz-turbo-bench fixtures` writes the same payload
byte for byte and packs it with the host's `7zz`, into a git-ignored
`bench/fixtures/<profile>/`; see `bench/fixtures/README.md`.

One trap, learned the expensive way: when the tree is copied to a bench host
with `rsync -a`, the source files arrive with their *original* mtimes, which
can be older than the `target/` artifacts already on that host. Cargo then
reports nothing to do and the run measures the previous binary — silently, and
plausibly, because the numbers look like the numbers you had before. Touch the
sources after the copy (`find src tools -name '*.rs' -exec touch {} +`), or
check something you know changed, before believing a remote "after" run.

## Acceptance gate for the codec swap

1. faster than upstream `sevenz-rust2` 0.22.2 on the same archive, and
2. within 5% of what `lzma-bench` reports for `lzma-turbo` on a bare LZMA2
   stream — i.e. the 7z container path must not eat the win.

For the multi-threaded path the second clause is measured *per thread count*
against `lzma-bench --threads 1,2,4,8` on the same fixture, not only at the
machine's full width. A block written by `7zz -mmt=on` has eight runs in it, so
at eight threads it is one batch and every scheduling bug in the reader is
invisible; the same bug costs 1.5x at two.

## Reading a decode's phases

`SEVENZ_TURBO_MT_TRACE=1` makes the parallel reader print, when a block's coder
is dropped, what that block's decode actually did:

```console
$ SEVENZ_TURBO_MT_TRACE=1 ./target/release/decode-bench --runs 1 --threads 2 \
    --only fork --no-oracle mt.7z
mt-trace: threads=2 spawned=2 drains=2 drain=10.768s sink=0.377s/8 small=0 MiB \
          pump=0.502s fed=897 MiB chased=0 MiB out=1024 MiB runs=8
```

- `chased` and `small` are the two ways the chase decoder shows itself: bytes
  this reader fed knowing they were not a whole run, and bytes that came back
  out of the decoder in pieces small enough to have come from it (it emits in
  1 MiB steps, a worker emits a whole run). On an archive with run boundaries
  both should be zero. On one without — `7zz -mmt=1` — `chased` should be
  nearly everything, and `fed` should track the decode rather than run ahead
  of it.
- `pump` against `drain` says whether the reader is feeding or waiting.
- `drains` is how many batches the block took: one or two is a block that fit
  the read-ahead, a thousand is the streaming path.

## Results

Measured 2026-09-16 and 2026-09-17 at sevenz-turbo 0.23.0 (on `lzma-fast`
0.2.0 to 0.3.0, since renamed `lzma-turbo`), with the human-oriented
`decode-bench` modes above. The crate and `lzma-turbo` (now 0.7.0) have
changed since; these are a dated record, not
current figures.

Three hosts, because the interesting number — what the parallel path does at
two, eight and all threads — is a property of the machine's cores as much as of
the code. Both fixtures are 1024.0 MiB of output; every figure is the median of
three runs with the box otherwise idle.

### linux-x86_64

12th Gen Intel Core i5-1240P: 4 performance cores with SMT (CPUs 0-7) and 8
efficiency cores (CPUs 8-15), 16 CPUs in total, no AVX-512. 61 GiB RAM,
rustc 1.98.1, 7-Zip 26.03 (x64, built from source with the assembly sources),
release profile with fat LTO.

A hybrid machine measures two different things depending on which cores a run
lands on, so every decoder was measured twice: once unpinned across all 16
CPUs, and once pinned to the performance cores with `taskset -c 0-7` — applied
identically to `7zz` and to upstream, not only to this crate.

#### `mt.7z` (897.5 MiB packed, LZMA2 written with multi-threaded chunking)

| --- | --- | --- | --- | --- |
| `7zz t` (all threads) | 3.860 s | 265.3 | 4.217 s | 242.8 |
| `7zz t -mmt=1` | 20.166 s | 50.8 | 20.085 s | 51.0 |
| `sevenz-rust2` 0.22.2 | 25.629 s | 40.0 | 28.862 s | 35.5 |
| `sevenz-turbo` @1 | 19.899 s | 51.5 | 19.882 s | 51.5 |
| `sevenz-turbo` @2 | 11.439 s | 89.5 | 11.394 s | 89.9 |
| `sevenz-turbo` @8 | 4.587 s | 223.2 | 5.057 s | 202.5 |
| **`sevenz-turbo` @16** | **4.599 s** | **222.6** | — | — |
| `sevenz-turbo` @16, no CRC | 4.596 s | 222.8 | 4.965 s (@8) | 206.2 |

#### `st.7z` (897.3 MiB packed, one single-threaded LZMA2 stream)

| --- | --- | --- | --- | --- |
| `7zz t` (all threads) | 20.069 s | 51.0 | 20.014 s | 51.2 |
| `7zz t -mmt=1` | 20.187 s | 50.7 | 20.102 s | 50.9 |
| `sevenz-rust2` 0.22.2 | 28.757 s | 35.6 | 28.597 s | 35.8 |
| **`sevenz-turbo` @1** | **19.970 s** | **51.3** | **19.781 s** | **51.8** |

| `sevenz-turbo` @8 | 21.163 s | 48.4 | 21.057 s | 48.6 |

A stream written without dictionary resets cannot be cut, so there is nothing
to decode in parallel and every thread count lands on the same number — 6%
behind one thread, which is what the read-ahead and the scan cost when they buy
nothing. `7zz` is in the same position: its own `-mmt` makes no difference on
this fixture either.

#### Against `lzma-turbo` itself

`lzma-bench --threads 1,2,4,8` on the same box and the same stream, without a
7z container around it: **20.000 s / 10.593 s / 6.512 s / 4.058 s**.

At the decoder's own boundary this crate matches that at every thread count —
10.77 / 6.65 / 4.05 / 4.12 s at 2 / 4 / 8 / 16 threads, measured with
`SEVENZ_TURBO_MT_TRACE=1`, which is within ~2% of bare. The end-to-end lane
above was 0.7 s slower at eight threads when first measured. Most of what
the reader did with each block then was copy it: it drained everything the
decoder had ready, spilled what did not fit the caller's buffer, and copied
that a second time on the way out. The reader now asks for no more than the
caller's buffer holds (`drain_upto`, lzma-turbo 0.3.0), which took the row
from 4.815 s to 4.587 s unpinned and 5.175 s to 5.057 s pinned; the table
above is the re-measured one (the @2 rows are from the earlier run). What
remains of the gap is the harness's digest of 1 GiB and the in-order copy
into the caller's buffer, which `7zz t` does not do.

#### What parallel decoding costs in memory

A run in flight costs its packed *and* its unpacked bytes at once, and the
batch fed between drains sets the peak. On the 897 MiB fixture, peak RSS is
about **2.58 GiB at two threads and 4.06 GiB at eight**, against 376 MiB for
the single-threaded path. `ArchiveLimits::memory` is the trade: a budget the
in-flight runs will not fit in decodes single-threaded rather than failing.
The upstream change that would remove the need to hold whole batches is the
chase-decoder request in `docs/lzma-turbo-requests.md`.

#### AES-256: AWS-LC against RustCrypto

Both cryptography backends decode the same archive, so the choice is a
performance question. Two fixtures, both 1 GiB of incompressible payload
written by `7zz a -pbench-passphrase`: `aes_store.7z` at `-mx0`, where AES (and
the CRC) is nearly all of the work, and `aes_mx1.7z` at `-mx1`, where LZMA2
dominates and AES is a few percent. Same box, same session, median of 3, the
tool built twice — `cargo build --release -p decode-bench` for AWS-LC and
`--features native-crypto` for RustCrypto — and run as
`decode-bench --runs 3 --threads 1,8 --password …`.

| Fixture | Lane | AWS-LC unpinned | RustCrypto unpinned | AWS-LC pinned | RustCrypto pinned |
| --- | --- | --- | --- | --- | --- |
| `aes_store.7z` (`-mx0`) | @1 | **0.282 s** | 0.374 s | **0.280 s** | 0.353 s |
| `aes_store.7z` (`-mx0`) | @8 | **0.300 s** | 0.346 s | **0.275 s** | 0.351 s |
| `aes_mx1.7z` (`-mx1`) | @1 | 21.339 s | 21.328 s | 21.231 s | 21.310 s |
| `aes_mx1.7z` (`-mx1`) | @8 | 20.051 s | 20.039 s | 20.193 s | 20.087 s |

For reference on the AES-dominated fixture, `7zz t -p` is 0.625 s unpinned and
0.567 s pinned, and upstream `sevenz-rust2` 0.22.2 (RustCrypto AES) is 0.938 s
and 0.932 s. Every lane produced the same digest, `c337ec4e6fd27584`.

AWS-LC wins the AES-dominated fixture by 20-25% at one thread and 15-25% at
eight, pinned or not. On the `-mx1` fixture the two are indistinguishable —
AES is not the bottleneck there, LZMA2 is, and the numbers say so.

The store fixture is not pure AES: the `no crc` rows put CRC-32 at about
0.03 s of it, and the bench's own digest costs another 0.04 s. It separates
the backends because it is the same work on both sides, not because it
isolates the cipher; `--cipher-only` does that.

#### Where the AES store fixture's time goes

`decode-bench` can price each layer separately, which is how the store
fixture's gap to `7zz t` was found and closed. `--cipher-only` decrypts 1 GiB
already in memory, in 1 MiB chunks with the IV carried between them, calling
`aws-lc-rs` directly; `--floor` reads the archive file in 1 MiB chunks and
optionally digests it, which is the floor no lane can beat; `--io-profile`
reports the read-size histogram of one decode; and the `no crc` lane prices
the checksum. On linux-x86_64, pinned:

| Layer | 1 GiB |
| --- | --- |
| Cipher alone (`--cipher-only`) | 0.124 s |
| File read alone (`--floor`) | 0.073 s |
| The bench's own digest (`--floor`) | 0.037 s |
| CRC-32 (`@1` minus `@1 no crc`) | 0.031 s |
| **Sum of the parts** | **0.265 s** |
| Measured `sevenz-turbo @1` | 0.280 s |

The parts add up, so there is nothing material left in the plumbing. That was
not true before this package: the AES decoder used to read the packed stream
512 bytes at a time into a fixed array, decrypt into a `Vec` and copy that into
the caller's buffer, and the same lane measured **0.862 s unpinned / 0.907 s
pinned** — three times what the parts cost. `--io-profile` now shows 1024
reads of 1 MiB for a 1 GiB archive; `strace -c` on the old binary counted
4.19 million `read` calls for the same archive, an average of 256 bytes each.

The backend comparison above is downstream of that fix. A decoder that hands
the cipher 256 bytes at a time pays a per-call cost four million times, and
AWS-LC's per-call cost is the higher of the two: before the fix this box put
AWS-LC *behind* RustCrypto on the store fixture (0.86 s against 0.37 s once
RustCrypto was rebuilt), which says nothing about either cipher. Sized in
1 MiB chunks, the cipher's own throughput is what the table shows.

The non-AES fixtures were re-measured on the same box after the change, to
show it cost nothing elsewhere: `mt.7z` 19.76 s @1 / 4.80 s @8 and `st.7z`
19.84 s @1 (pinned), against 20.00 s, 4.82 s and 20.10 s before — inside the
run-to-run spread.

Two plumbing items were considered and dropped on these numbers: overlapping
the CRC with the decrypt (worth at most 0.031 s, under the 0.1 s bar) and a
one-chunk-ahead reader (the read is 0.073 s of a 0.280 s lane, and it is page
cache, not a device). Both would add a thread or a buffer for single-digit
percentages.

### windows-x86_64 (Ryzen 5 3600, 6 cores / 12 threads)

A second host, so the tables are not one machine's opinion: Zen 2, AES-NI and
AVX2 but no VAES, `rustc` 1.97.1 on `x86_64-pc-windows-msvc`, and 7-Zip 22.01
as the oracle. No pinning tool is used here; everything is unpinned, median
of 3, on an otherwise idle box.

| Fixture | Lane | `sevenz-turbo` | `7zz t` | upstream 0.22.2 | vs `7zz` |
| --- | --- | --- | --- | --- | --- |
| `aes_store.7z` (`-mx0`, AES) | @1 | **0.481 s** | 0.652 s | 3.464 s | 0.738 |
| `aes_store.7z` | @8 | **0.472 s** | 0.652 s | 3.464 s | 0.724 |
| `aes_mx1.7z` (`-mx1`, LZMA2+AES) | @8 | 18.032 s | 2.563 s | 4.923 s | 7.04 |
| `mt.7z` (chunked LZMA2) | @12 | 4.356 s | 3.269 s | 10.561 s | 1.33 |
| `st.7z` (one LZMA2 stream) | @1 | **20.095 s** | 20.223 s | 31.480 s | 0.994 |

The shape matches the Linux box: level with `7zz` on a single LZMA2 stream,
behind it on a chunked one (7-Zip's `-mx1` and `mt` lanes use all 12 threads
against our 8/12 and win), and ahead of it where AES dominates. Every lane
produced the same digest as every other host, `c337ec4e6fd27584`.

On this host the AES store fixture splits as: the cipher alone 0.138 s for
1 GiB (7.4 GiB/s, `--cipher-only`), the full chain with checksums off 0.405 s,
and with them on 0.473 s — so CRC-32 is 0.068 s and everything that is neither
cipher nor CRC is 0.267 s. The RustCrypto lane on the same fixture is 0.650 s
at one thread against AWS-LC's 0.481 s.

#### Proving the AWS-LC lane builds from source

`aws-lc-sys` ships pre-assembled NASM objects and this crate enables its
`prebuilt-nasm` feature, which is what a consumer on Windows gets by default
and what every number above was measured with (`db-prebuilt.exe`). That
default would hide a broken from-source build, so both paths are built:

- Default (`prebuilt-nasm`, no NASM anywhere on `PATH`): builds.
- Feature removed, `AWS_LC_SYS_PREBUILT_NASM=0`, NASM removed from `PATH`,
  `aws-lc-sys`'s build directory deleted first so the build really re-runs:
  fails, with `NASM command not found! Build cannot continue.` from
  `aws-lc-sys`'s `nasm_builder.rs`. That failure is the proof that the
  assembly is genuinely being assembled rather than taken from the shipped
  objects.
- Same, with `C:\nasm\nasm-3.01` back on `PATH`: builds.

Both binaries decode `aes_store.7z` to the same digest, `c337ec4e6fd27584`.
The toolchain for either is Visual Studio 2022's `VsDevCmd.bat -arch=x64`,
`clang-cl` as `CC`/`CXX`, and `AWS_LC_SYS_STATIC=1`.

### macOS arm64 (Apple M5 Max, 18 cores)

Same tool, same fixture recipes, `7zz` 26.01 as the oracle, median of 3, taken
with the machine's one-minute load under 3. The payload here is generated
locally, so the digest differs from the Linux and Windows hosts
(`74a0ed05e6216bb6`); every lane on this host agrees on it.

#### `mt.7z` and `st.7z`

The parallel series, re-measured after the read-ahead rewrite (load 2.5 at the
start of the run, `7zz` 26.01, median of 3, unpinned — this machine has no
efficiency/performance split worth pinning around for a decode).

| Decoder | `mt.7z` (chunked LZMA2) | `st.7z` (one stream) |
| --- | --- | --- |
| `7zz t` (all threads) | 2.134 s | 15.133 s |
| `7zz t -mmt=1` | 14.883 s | 15.003 s |
| upstream 0.22.2 @16 | 23.689 s | 24.120 s |
| `sevenz-turbo` @1 | 14.913 s | **14.965 s** |
| `sevenz-turbo` @2 | 7.895 s | 15.265 s |
| `sevenz-turbo` @8 | **2.276 s** | 15.328 s |
| `sevenz-turbo` @18 | 2.278 s | 15.362 s |

1.59x upstream at one thread and 10.4x at eight on the chunked fixture, within
7% of `7zz` at eight threads, and level with `7zz` (0.99) on the single stream
where neither decoder can use more than one core. Threads past eight buy
nothing on this fixture: past eight the chunks run out. On `st.7z` more
threads cost a little,
which is the parallel path paying for machinery it cannot use — the reason the
reader falls back to the single-threaded path when a folder has one chunk.

## Differential extraction

Throughput is only interesting if the bytes are right. `tests/differential_7zz_tests.rs`
builds archives with `7zz a` across the method matrix (LZMA and LZMA2 at
`-mx1/5/9`, `-mmt=1` and `-mmt=on`, solid and non-solid, BCJ, BCJ2, delta,
AES-256 with and without an encrypted header, and a `-v256k` split set read as
one concatenated stream), extracts each with `7zz x` and with this crate, and
compares every member byte for byte. The suite skips itself when `7zz` is not
on `PATH`, which is the case on the CI runners; run it locally before
proposing any decoder change.
